# Harness de Evaluación RAG+LLM — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un runner reproducible que puntúe el asistente RAG+LLM contra una muestra fija versionada, con verdad calculable por pandas, y que produzca deltas comparables entre corridas.

**Architecture:** Módulo `backend/eval/` (scoring puro → casos con verdad calculable → runner con aislamiento del estado real) + CLI. El runner entra por `TestClient` al endpoint real `/ask`. Antes se hacen cuatro cambios mínimos en la capa de IA para que la respuesta exponga `grounding_rechazado` y `rag_examples_used` (hoy invisibles en no-stream), y el bloque few-shot se ordene en positivos/negativos separados.

**Tech Stack:** Python 3 (venv `backend/`), pandas, FastAPI TestClient, pytest. qwen2.5:3b vía Ollama solo en la corrida de validación final.

**Spec:** `docs/superpowers/specs/2026-10-29-eval-rag-design.md`

## Global Constraints

- qwen2.5:3b es el único modelo; no usar el 7B (hardware: GTX 1060 6 GB).
- `k = 8` (`n_results` por defecto del endpoint); `MAX_EXAMPLES = 2`.
- Nunca escribir `backend/data/ai_config.json` ni `backend/data/feedback.json` desde el eval (aislamiento).
- Verdad calculable pandas, sin juez LLM, sin respuestas doradas.
- Precisión@k en preguntas anchas (`len(expected) > 2*k`); nunca recall sobre anchas.
- Tests puros sin red/LLM/servidor; la validación del runner es una corrida real, no pytest.
- Mensajes de commit en ASCII sin tildes (convención del repo). Windows: `sys.stdout.reconfigure(encoding="utf-8")` en CLIs.
- Comandos: pytest desde `backend/` con `backend\.venv\Scripts\python.exe -m pytest`; commits con `git commit -F <archivo>` (PowerShell sin heredoc).

## Review Focus

Las cinco condiciones que más probablemente rompan esto y que los tests deben castigar:

1. **Índice RAG aún construyendo al empezar los casos** → respuestas solo léxicas sin que nadie lo note. *Espera activa a `rag_store.has_index()` tras el `done`; si no indexa en 120 s, el runner falla explícitamente (Task 6, test de la espera con has_index en False→True).*
2. **Caché en RAM de `feedback_store._cache`** → redirigir `FEEDBACK_PATH` sin limpiarla hace que la corrida lea la memoria real del analista. *Test en Task 6: `_isolated_store()` deja `_load() == []` aunque exista un feedback.json real.*
3. **Números que no son la cifra buscada** (IPs como `10.10.97.1`, fechas, `Log_ID`) → falsos positivos en agregados. *`number_in_answer` acepta solo el número más cercano a la unidad declarada; tests en Task 1 con frases que mezclan IP + cifra.*
4. **IDs reales de otra parte del dataset** citados por el LLM → el guard **sí los rechaza** (por diseño: `_grounding_ok` valida contra la evidencia recuperada, no contra el dataset entero), pero el runner debe distinguir «rechazo del guard» de «ID ni siquiera del dataset» (`ids_inventados` = 0 tras pasar el guard). Un ID real-y-relevante pero fuera de `expected` no es inventado y la precisión@k lo castiga solo como impertinente. *Tests separados en Task 1 (scoring: precisión penaliza IDs extraños) y Task 4 (guard: ID real fuera de evidencia → `grounding_rechazado`, engine determinista).*
5. **`--motor determinista` contaminado** → si el monkeypatch de `ai_config.get` no se restaura o no alcanza a `answer_question`, la línea base miente. *Context manager con test: tras salir del bloque, `ai_config.get()` es el original (Task 6); y la corrida de validación usa `--motor ambos` (Task 7).*
